# Development fixture adapters

The Results fixture preview and generation inspector use these development-only adapters, separate from the implemented authenticated FE-04 real flow. Original shared JSON and manifest metadata remain in `../../../docs/fixtures/`; these adapters do not copy prototype prices or provide real API responses.

- `resultsFixtures.ts` loads all six success scenarios: within budget, over budget, partial prices, no prices, unknown taxes, and known minimum over budget. It preserves the manifest and selected case metadata for the Results preview at `/results`, offered only when no retained real result exists. Rendering always carries visible MOCK/sample labels, including provider-shaped prices. Direct navigation without a retained real response or deliberately selected fixture shows an empty state.
- `generationMocks.ts` loads the five repository error fixtures with original bodies, HTTP statuses, headers, request IDs and manifest/case metadata. Missing unsupported-location/date, provider-unavailable and internal-error examples are separately marked `development_example`. Its pending preview does not report verified provider progress or produce a successful trip.

Structural fixtures retain `data_mode=structural_mock`, `live_evidence=false`, and their fixed validation-date context. They never prove current provider coverage, availability or live prices. Fixture type assertions rely on repository fixture validation; they are not a full runtime schema/semantic validator for untrusted HTTP responses.

Both adapters are reached through DEV-gated preview components. Their controls and fixture imports are excluded from production assets, as checked by the Results tests. They never silently replace failed online responses or bypass authentication.

Supabase Auth and the reusable FastAPI transport are implemented separately from these fixture adapters. Diyar reported real JWT probe testing against backend PR #23 commit `e4fe192`, with ES256 signing: Account A and Account B each received HTTP 200 with matching identity; a missing JWT received HTTP 401 UNAUTHORIZED. See the [frontend verification record](../../README.md#be-02-auth-and-jwt-verification). This evidence does not turn fixture prices into live data or connect fixtures to the backend.

Real generation uses Login → Trip Planner → authenticated `POST /api/v1/trips/generate` → adopted v0.4 runtime structure/reference validation → account-bound in-memory Results. See the [service boundary](../services/README.md). Local city suggestions derive from the adapter's authoritative 80-city mapping and normalization; they do not call providers or guarantee offers. Real results retain backend-selected offers, taxes, sources, UTC retrieval timestamps, warnings, null costs and budget totals/statuses without frontend recalculation. They say Retrieved price, not Live: retrieval does not guarantee current availability. Neither fixtures nor demo data replace failed generation.

Loading, expiry/sign-in actions, safe field/service errors, duplicate prevention, Retry-After cooldown and deliberate retries belong to the real lifecycle. Identity changes/signout invalidate pending operations, including A → B → A; late success/error cannot revive them. No automatic generation retry is introduced by fixtures. A selected fixture never authenticates a user, completes a pending generation or enters the real Results handoff.
