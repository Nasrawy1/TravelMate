# TravelMate — Database Schema

**Version:** 0.2 (Backend-only access and security baseline)  
**Status:** Proposed security baseline — ready for team review; execute migration only when F-09 is approved  
**Project:** TravelMate Graduation Project  
**Related documents:** `architecture.md` v1.1, `mvp-scope.md` v1.2, `api-contracts.md` v0.3

## 1. Purpose and MVP Boundary

TravelMate uses **Supabase Auth** for account management and **Supabase PostgreSQL** only for data that must be saved between sessions.

- **Must Have:** Sign-up/sign-in/sign-out through Supabase Auth. Supabase manages its own `auth.users` records; TravelMate does **not** need a duplicate `public.users` or `profiles` table for the MVP.
- **Must Have:** Trip generation. `POST /api/v1/trips/generate` does **not** write to the database; the generated response can be displayed immediately.
- **Should Have (F-09):** Save, list, and reopen generated trips. This feature introduces one application table: `public.trips`.
- **Must Have:** Offline demo mode. It uses read-only fixtures bundled with the frontend, **not** Supabase or the `trips` table.

**Decision:** Design the optional storage now, but do not make it a blocker for the core AI + one-live-travel-API MVP. The database table and saved-trip endpoints are implemented only when the team starts F-09.

**Approved access path for F-09:** React uses Supabase **Auth** only. All application-table reads and writes go through authenticated **FastAPI** endpoints. The browser has no direct `public.trips` privileges. FastAPI verifies the user's token and uses a server-only Supabase elevated key for database access; because the elevated role bypasses RLS, FastAPI itself must enforce user ownership on every operation.

## 2. Minimal Entity Relationship

```text
Supabase-managed authentication           TravelMate application data

    auth.users                                 public.trips
    ----------                                 ------------
    id (UUID, PK)  1 -------------------- N    user_id (UUID, FK)
                                                 id (UUID, PK)
                                                 trip input summary
                                                 trip_snapshot (JSONB)
                                                 created_at
```

- One authenticated user may have zero or many saved trips.
- Each saved trip belongs to exactly one authenticated user.
- Deleting an authentication user cascades to that user's saved trips.
- Flights, hotels, activities, and prices are **not** separate database tables in this MVP; their normalized result is stored as one snapshot when a user explicitly saves a trip.

## 3. Table: `public.trips` (Should Have)

| Column | PostgreSQL type | Rule / purpose |
|---|---|---|
| `id` | `uuid` | Primary key; generated by PostgreSQL |
| `user_id` | `uuid` | Required foreign key to `auth.users(id)`; **set from verified authentication**, never trusted from request JSON |
| `departure_city` | `text` | Canonical supported city label at time of generation |
| `destination_city` | `text` | Canonical supported destination label |
| `start_date` | `date` | Trip start date |
| `return_date` | `date` | Trip end/return date; 1–7 nights after start |
| `adults` | `smallint` | Integer from 1 through 4 |
| `budget_usd` | `numeric(12,2)` | Whole-trip USD budget; positive |
| `contract_version` | `text` | Version actually used to validate the snapshot (initially `0.3`); explicitly supplied by FastAPI, not a DB default |
| `trip_snapshot` | `jsonb` | Validated, sanitized full generated result, including itinerary, budget, selected offer IDs, source labels, and warnings |
| `created_at` | `timestamptz` | Server-generated time the user saved the trip (UTC-capable) |

**Why JSONB?** The day-by-day itinerary and flight/hotel result shapes are nested and may evolve as providers change. For the MVP, one snapshot avoids unnecessary `days`, `activities`, `flights`, `hotels`, and `prices` tables. The listed scalar columns still allow efficient saved-trip summaries and filtering.

**Snapshot rules:**

1. Persist a response that passed `api-contracts.md` v0.3 validation, with `generation_status: "complete"`. It may have `live_integration_status: "no_price"` and `budget.status: "uncertain"`.
2. Keep provider names, price origin labels, `retrieved_at`, selected-offer references, missing categories, and warnings intact. Preserve `null` for unknown prices.
3. Store **only** necessary normalized result fields. Never store Supabase access tokens, third-party API keys, raw provider responses, passport/payment details, or debug secrets.
4. `created_at` is the **save time**, not the time any quoted price was retrieved. A saved quote is historical; displaying a saved plan must not imply its offers are currently available or bookable.
5. FastAPI must ensure the scalar summary fields agree with the `trip_snapshot.trip` values. Database `CHECK` constraints enforce basic limits, but do **not** validate the full nested JSON schema.
6. FastAPI validates the payload using the agreed response schema, verifies that selected offer IDs reference returned offers, recomputes/compares basic summary fields, and enforces a configured snapshot-size limit before insertion. Never treat client-supplied provider labels as proof of a live quote.
7. **F-09 trust decision:** Save/reopen stores a schema-validated **user-submitted historical snapshot**, not a cryptographically verified generation record. It may be changed by the browser. The UI must label reopened offers as a **saved copy — unverified and potentially outdated**; do not use saved snapshots as evidence for the live-integration MVP acceptance test. Server-signed generation receipts and re-quoting are deferred outside F-09.

## 4. Proposed SQL Migration (only for F-09)

**Implementation decision:** This migration permits the elevated **server-side** `service_role` to `SELECT` and `INSERT` only. Neither `anon` nor `authenticated` receives privileges on `public.trips`. There are **no end-user RLS policies**: with grants removed, browsers cannot query or write the table through the Supabase Data API. RLS remains enabled as an additional safeguard against accidentally exposing a new lower-privilege database role; it does **not** protect queries made as `service_role`.

Run the following **only after F-09 is prioritized and reviewed**. It targets a **fresh database table**; do not blindly apply it over an existing table or existing policies. Run it as a migration/SQL Editor operation with suitable administrative privileges.

```sql
begin;

create table public.trips (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null references auth.users(id) on delete cascade,
    departure_city text not null,
    destination_city text not null,
    start_date date not null,
    return_date date not null,
    adults smallint not null,
    budget_usd numeric(12, 2) not null,
    contract_version text not null,
    trip_snapshot jsonb not null,
    created_at timestamptz not null default now(),

    constraint trips_departure_not_blank
        check (length(btrim(departure_city)) > 0),
    constraint trips_destination_not_blank
        check (length(btrim(destination_city)) > 0),
    constraint trips_distinct_cities
        check (lower(btrim(departure_city)) <> lower(btrim(destination_city))),
    constraint trips_duration
        check ((return_date - start_date) between 1 and 7),
    constraint trips_adults
        check (adults between 1 and 4),
    constraint trips_budget_positive
        check (budget_usd > 0),
    constraint trips_snapshot_is_object
        check (jsonb_typeof(trip_snapshot) = 'object')
);

create index trips_user_created_idx
    on public.trips (user_id, created_at desc);

-- RLS remains enabled. There are deliberately NO policies granting
-- anon/authenticated access: app data is available through FastAPI only.
alter table public.trips enable row level security;

-- Remove automatic/default table grants, including privileges that
-- RLS alone does not guard (e.g., TRUNCATE).
revoke all privileges on table public.trips
    from public, anon, authenticated, service_role;

-- Supabase elevated server-side access: enough for INSERT ... RETURNING
-- and SELECT, but no UPDATE/DELETE/TRUNCATE grant through this table.
grant select, insert on table public.trips to service_role;

commit;
```

**Permission model:** Supabase's service/elevated role has `BYPASSRLS`. Therefore **RLS policies cannot enforce ownership for these backend calls**. FastAPI must always verify the Supabase user JWT and use an explicit `user_id` filter for list/read operations. It must supply `user_id` itself on inserts. A valid token from User A must never authorize access to User B's data.

**Migration checks:** After execution in a **test** Supabase project, run the following as a database administrator to inspect effective grants and the RLS flag. Expected: `anon` and `authenticated` return `false` for SELECT/INSERT, `service_role` returns `true` for SELECT/INSERT and `false` for UPDATE/DELETE/TRUNCATE, and `rls_enabled` is `true`. Database-owner privileges are intentionally not covered by this table-role check.

```sql
select
    has_table_privilege('anon', 'public.trips', 'SELECT') as anon_can_select,
    has_table_privilege('anon', 'public.trips', 'INSERT') as anon_can_insert,
    has_table_privilege('authenticated', 'public.trips', 'SELECT') as user_can_select,
    has_table_privilege('authenticated', 'public.trips', 'INSERT') as user_can_insert,
    has_table_privilege('service_role', 'public.trips', 'SELECT') as backend_can_select,
    has_table_privilege('service_role', 'public.trips', 'INSERT') as backend_can_insert,
    has_table_privilege('service_role', 'public.trips', 'UPDATE') as backend_can_update,
    has_table_privilege('service_role', 'public.trips', 'DELETE') as backend_can_delete,
    has_table_privilege('service_role', 'public.trips', 'TRUNCATE') as backend_can_truncate,
    (select relrowsecurity from pg_class where oid = 'public.trips'::regclass) as rls_enabled;
```

Confirm from a separate client using a real signed-in user that direct Supabase Data API reads/inserts are denied, while FastAPI can perform them after its own JWT/ownership checks. Do not depend on project-wide default grants; this migration sets table grants explicitly. Do not add client-facing `SELECT`/`INSERT` RLS policies unless the architecture is deliberately changed and reviewed.

**Operational security:** A Supabase secret/service-role key is **elevated across the project**, not merely for this table; restricting `public.trips` grants does not turn it into a narrowly scoped credential. Use a dedicated **non-production Supabase project** for the graduation demo. Put the Supabase secret/service-role key only in FastAPI's server environment (`.env` locally, excluded by `.gitignore`). Never use a `VITE_`-prefixed variable for it, return it in responses, or commit it. A source-code handover running on the evaluator's computer cannot conceal local secrets from that machine's owner: use limited/demo project credentials where possible, rotate/revoke them after evaluation, and avoid sharing production secrets.

**Future migrations:** If this table or policies already exist, inspect them and write an incremental migration instead of re-running this fresh-table SQL. `contract_version` is required and must be written explicitly by FastAPI as the schema version actually validated.

## 5. Authentication and Authorized Data Access

### Sign-up / sign-in

1. React uses the Supabase Auth SDK to register and sign in.
2. Supabase Auth manages `auth.users` and returns an access token.
3. React sends `Authorization: Bearer <access_token>` to protected FastAPI endpoints.
4. FastAPI verifies the token, extracts the authenticated user ID, and enforces ownership before responding.

### Saving / loading a trip (F-09 only)

1. **Generate:** `POST /api/v1/trips/generate` returns the itinerary without saving it.
2. **Save:** A separate authenticated `POST /api/v1/trips` submits a validated generated-result snapshot; FastAPI derives `user_id` from the verified token, validates the data, and inserts it.
3. **List:** Authenticated `GET /api/v1/trips` returns saved-trip summaries for **the requesting user only**, newest first; the full JSONB snapshot need not be sent in list results.
4. **Reopen:** Authenticated `GET /api/v1/trips/{trip_id}` returns the saved trip and snapshot only when it belongs to the requesting user; otherwise respond `404` without disclosing another user's trip.

**Fixed data-access design (not optional):** React uses the Supabase Auth client for login/session management, **never** the Supabase Data API for `public.trips`. FastAPI independently verifies each bearer token (signature, issuer/audience as appropriate, expiration) and extracts the user ID. A **separate server-only Supabase client** uses a secret/service-role key for `public.trips` queries. Do not replace the end-user's identity with the service-role identity for authorization decisions; this elevated client bypasses RLS.

**Required FastAPI authorization behavior:**

- `POST /api/v1/trips`: **ignore/reject any client-supplied `user_id`**; insert `user_id` from the verified JWT. Validate the snapshot and derive summary fields from it; never accept client-supplied owner/DB metadata as authoritative. `contract_version` is explicitly set by FastAPI.
- `GET /api/v1/trips`: filter **`user_id == verified_user_id`** in the database query; order by `created_at` descending. Use a finite page size when F-09 is implemented.
- `GET /api/v1/trips/{trip_id}`: query by **both** `id == trip_id` **and** `user_id == verified_user_id`; return `404` if no record matches, including a record owned by someone else.
- Deny missing, expired, incorrectly signed, or otherwise invalid user tokens with `401`. Never accept a client-supplied user ID as proof of ownership.
- Do not implement trip `UPDATE` or `DELETE` in F-09; the SQL grants neither privilege to `service_role` for this table.

**F-09 snapshot integrity decision:** The client may alter the generated JSON before calling Save. For the optional MVP save feature, accept **validated user-submitted historical copies** only, not provider-verified evidence. Recalculate/check deterministic fields and enforce size limits; label reopened prices as saved/unverified historical information. Re-querying providers or signing generation receipts would be a separate enhancement. This does not change the requirement that *normal live generation* must call a real provider through FastAPI.

## 6. API-to-Database Mapping (F-09)

| Public API field or action | Database storage |
|---|---|
| `trip.departure_city`, `trip.destination_city` | `departure_city`, `destination_city` |
| `trip.start_date`, `trip.return_date`, `trip.adults` | `start_date`, `return_date`, `adults` |
| Original `budget.budget_usd` | `budget_usd` |
| Full generated response: `itinerary`, `travel_options`, `budget`, `warnings`, status fields | `trip_snapshot` (JSONB) |
| Contract version used to validate and store the result | `contract_version` |
| Authenticated user from verified token | `user_id` |
| Time of explicit Save Trip action | `created_at` |

`budget.selected_flight_offer_id` and `budget.selected_hotel_offer_id` remain **inside** the snapshot; offer IDs are not foreign keys to persistent flight/hotel records. There is no stored generated-trip ID until a save succeeds, at which point the database creates `public.trips.id`.

**Contract dependency:** The exact JSON body and responses for the Should Have saved-trip endpoints remain **provisional** in `api-contracts.md` v0.3. Define and review those HTTP schemas before Adel and Diyar implement saving; this document alone does not finalize their API contract.

## 7. Data Lifecycle, Reliability and Local Demo

- **Normal mode:** Supabase Auth works online. Saved trips, if implemented, are stored on the hosted Supabase Free Tier and require internet access to read or save.
- **Offline demo:** Use local read-only fixtures. No Supabase login, database queries, or writes. A generated demo trip must not appear as a real saved user trip.
- **Data retention:** Keep saved trips until an authorized future deletion workflow or account deletion; explicit user-facing trip deletion is not part of the MVP. Account deletion is not implemented as a custom TravelMate feature.
- **Stored price freshness and trust:** Saved prices are user-submitted, timestamped historical snapshots; show a **saved copy — unverified and potentially outdated** label when reopened. They are not evidence of new, currently bookable, provider-verified offers.
- **Quotas and recovery:** Monitor Supabase Free Tier usage and account for network outages. Offline demo should still work even if the online Supabase project is unavailable.

## 8. Acceptance Tests for the Database Design

### Authentication — Must Have

- [ ] User sign-up/sign-in/sign-out functions through Supabase Auth.
- [ ] FastAPI rejects missing, expired, or invalid access tokens on protected endpoints.
- [ ] No duplicate `public.users` table or unnecessary profile data is required.

### Saved trips — Should Have (test only if F-09 is implemented)

- [ ] User A can save and list their own trips.
- [ ] User A cannot read User B's saved trips, even when guessing a valid trip UUID.
- [ ] A request cannot choose an arbitrary `user_id` to save a trip on another account.
- [ ] Direct Supabase Data API `SELECT`/`INSERT` on `public.trips` is denied for **both** `anon` and `authenticated` roles, including a correctly signed-in user.
- [ ] Backend `service_role` can `SELECT` and `INSERT` through FastAPI, but table-level `UPDATE`/`DELETE`/`TRUNCATE` are not granted to it; RLS remains enabled.
- [ ] Using User A's valid JWT, FastAPI cannot return User B's trip in list or detail; it uses explicit `user_id` filters because the elevated key bypasses RLS.
- [ ] Saving an invalid date range, invalid adult count, or non-positive budget fails validation.
- [ ] A valid complete itinerary with unavailable live prices and an `uncertain` budget can be saved; missing amounts remain `null`.
- [ ] Saved snapshots preserve selected offer IDs, provenance labels, and retrieval timestamps where present.
- [ ] Reopened saved prices are labeled **saved/unverified historical copies**, not confirmed current offers.
- [ ] Tampered user-submitted snapshots never count as proof of successful live travel-price integration; invalid JSON/fields/size are rejected by FastAPI.
- [ ] List endpoint returns lightweight summaries; single-item retrieval returns the stored snapshot.
- [ ] Attempts to update or delete trips through the normal user role are denied (features not implemented).
- [ ] When a user is removed from Supabase Auth, corresponding `public.trips` rows are removed by the FK cascade.

### Handover — Must Have

- [ ] Normal online authentication works on a second computer following the README.
- [ ] Offline demo works on a second computer with no Supabase connection.

## 9. Open Decisions and Next Steps

**Resolved in v0.2:** F-09 remains **Should Have** with one `public.trips` table; all saved-trip operations pass through FastAPI; the backend alone uses an elevated Supabase key; direct `anon`/`authenticated` table access is forbidden; backend `user_id` filters enforce ownership; saved snapshots are unverified historical user content (not live-price proof).

**Remaining implementation tasks:**

1. When F-09 is prioritized, define exact `POST /api/v1/trips`, `GET /api/v1/trips`, and `GET /api/v1/trips/{trip_id}` request/response schemas in `api-contracts.md`; the three endpoints are still **provisional** there.
2. Review this fresh-table migration with Adel, then execute it only in a test Supabase project and run privilege, direct-access, cross-user, and payload-validation tests before using it for the final demo.
3. Ziyad's real travel-price provider feasibility test remains independent of the optional `trips` table.
4. Implementation order: Supabase Auth + FastAPI JWT verification -> real AI/one live-price flow -> optional `trips` migration and saved-trip endpoints.

**Scope protection:** Do not add `profiles`, `hotels`, `flights`, `activities`, `bookings`, `payments`, `api_logs`, or analytics tables unless a separately approved feature actually needs them.
